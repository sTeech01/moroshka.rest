# Сайт ресторана «Морошка»

Next.js 16 (App Router, Cache Components) · Payload CMS 3 (SQLite) · Tailwind 4 · Zustand · Zod.
ТЗ: [`../tz-moroshka-site.md`](../tz-moroshka-site.md) · открытые вопросы: [`../open-issues.md`](../open-issues.md).

## Запуск

```bash
npm install
cp .env.example .env.local   # PAYLOAD_SECRET обязателен для прода; в dev есть запасной
npm run dev                  # сайт: http://localhost:3000, админка: http://localhost:3000/admin
```

- **Первый запуск** создаёт базу `data/payload.db` и заполняет её текущим контентом сайта (тексты, фото, настройки — см. `src/payload/seed`).
- **Первый пользователь:** откройте `/admin` и зарегистрируйтесь. Первый пользователь автоматически становится администратором.
- Заказы, брони и заявки на банкет уходят сотрудникам в Telegram (`TELEGRAM_*`) и/или беседу ВКонтакте (`VK_*`) — во все заполненные каналы (`src/lib/notify`). Без них в dev выводятся в консоль сервера.
- Проверки: `npm run typecheck`, `npm run lint`, `npm run cms:check` (CMS без Next), `npm run build`.

## CMS (Payload)

Админка — `/admin`, на русском. Меню, цены и фото блюд в CMS **не** редактируются: они приходят из iiko.

| Раздел админки | Что там | Где на сайте |
|---|---|---|
| Контент → Афиша | События: дата, обложка, описание. Прошедшие скрываются сами | Главная, `/events` |
| Контент → Промо и акции | Баннеры с датами показа, место: главная и/или меню и доставка | Главная, `/menu`, `/delivery` |
| Контент → Страницы | О ресторане, условия доставки, соглашение, оферта, правила | `/about`, низ `/delivery`, `/privacy-policy`, `/offer`, `/rules` |
| Контент → Медиа | Все загруженные фото. Оригинал ужимается до 2400 px и переводится в WebP | — |
| Страницы → Главная | Тексты и фото блоков, **популярные блюда** (выбор из меню iiko), галерея | `/` |
| Страницы → Банкеты и VIP-зал | Фото первого экрана, залы, галерея, текст | `/banquets` |
| Настройки → Ресторан | Телефоны, адрес, часы, соцсети, координаты, реквизиты | Шапка, подвал, `/contacts` |
| Настройки → Доставка | Вкл/выкл доставки, объявление, мин. сумма, стоимость, бесплатно от, часы приёма, слоты, самовывоз | Корзина, оформление, проверка заказа на сервере |
| Администрирование → Пользователи | Роли: администратор (всё) и редактор (контент) | — |

**Как правка попадает на сайт.** После сохранения хуки Payload сбрасывают кэш с тегом `content` (`src/payload/revalidate.ts`), и следующий запрос получает свежие данные. Деплой не нужен.

**Изменили поля коллекций или глобалов (`src/payload/**`)?**

```bash
npm run generate:types            # src/payload-types.ts
npm run generate:importmap        # если добавили/убрали свои компоненты админки
npm run migrate:create <название> # миграция для прода — закоммитить src/migrations
```

В dev схема базы синхронизируется сама. В продакшене при старте применяются миграции из `src/migrations` (`prodMigrations`).

**Данные на сервере:** база (`DATABASE_URL`) и папка `media/` с загруженными фото. Их нужно хранить вне папки релиза и бэкапить. В git они не попадают.

## Архитектура

```
src/
  app/(site)/          сайт: свой корневой layout, страницы, 404
  app/(payload)/       админка и REST API Payload (/admin, /api/<коллекция>) — файлы из шаблона Payload
  app/api/orders       приём заказа: валидация → пересчёт по меню и условиям доставки → OrderSink → (онлайн) PaymentGateway
  app/api/booking      бронь стола / заявка на банкет → Telegram
  app/api/address      подсказки улиц Губкинского (DaData)
  app/api/menu-options список блюд для виджета «Популярные блюда» в админке
  app/api/revalidate   сброс кэша меню (для вебхуков iiko)
  payload.config.ts    конфиг CMS
  payload/             коллекции, глобалы, доступы, хуки сброса кэша, сид, виджет админки
  lib/content.ts       чтение контента из Payload (локальный API) с кэшем
  lib/delivery.ts      тип условий доставки и расчёт стоимости — общий для браузера и сервера
  lib/iiko/            типы ответов iikoCloud и HTTP-клиент с токеном
  lib/menu/            доменная модель меню, маппер iiko → сайт, кэшируемое получение меню
  lib/providers/       адаптеры: MenuSource, OrderSink, PaymentGateway (mock ↔ real)
  lib/cart/pricing     цена позиции и проверка модификаторов — общая для браузера и сервера
  store/cart.ts        корзина (Zustand + localStorage)
data/iiko-mock/        заглушка iiko: ответы /api/2/menu/by_id и /api/1/stop_lists
```

### Провайдеры (переключаются в `.env`)

| Переменная | Сейчас | После подключения |
|---|---|---|
| `MENU_PROVIDER` | `mock` — читает `data/iiko-mock/*.json` | `iiko` — iikoCloud `/api/2/menu/by_id`, `/api/1/stop_lists` |
| `ORDER_PROVIDER` | `telegram` — заказ сообщением сотрудникам (Telegram и/или ВКонтакте) | `iiko` — `/api/1/deliveries/create` |
| `PAYMENT_PROVIDER` | `mock` — оплата «проходит» сразу | `yookassa` / `tbank` (реализовать в `lib/providers/payment/`) |
| `NEXT_PUBLIC_ONLINE_PAYMENT_ENABLED` | `false` — пункт «Онлайн» скрыт | `true` |

Заглушка меню хранится **в формате ответа iiko**, поэтому общий маппер `lib/menu/map-iiko.ts` работает одинаково для обоих источников.

**Сейчас в заглушке — реальное меню ресторана** из текущего сервиса доставки myresto, который работает поверх iiko. ID блюд и организации — настоящие ID из iiko. Обновить снимок: `npm run menu:import` (стоп-лист myresto не отдаёт, он пустой). После подключения iikoCloud ID не изменятся: корзины и «популярные блюда» сохранятся.

### Два меню: «Меню» и «Доставка»

| Раздел | Что это | Источник |
|---|---|---|
| `/menu` | Меню зала: витрина без корзины, все блюда кухни | `getHallMenu()` → `data/iiko-mock/hall-menu.json`, позже — второе внешнее меню iiko (`IIKO_HALL_MENU_ID`, опц. `IIKO_HALL_PRICE_CATEGORY_ID`) |
| `/delivery` | Заказ: только то, что возят. Ниже — условия доставки из CMS | `getMenu()` → меню доставки iiko (`IIKO_EXTERNAL_MENU_ID`) |

Связь по **ID блюда в iiko**: если блюдо зала есть в доставке и не в стоп-листе, у него ссылка «Можно заказать домой». Если у блюда доставки нет фото в iiko, берётся фото того же блюда из меню зала. Противоречий в названиях и составах нет, пока это одна номенклатура iiko; цены у меню зала и доставки свои (разные ценовые категории).

Меню зала перенесено со старого сайта (moroshka.rest/menu-kitchen, 23 страницы-картинки): `scripts/hall-menu/source.mjs` — данные, `npm run menu:hall -- <папка со страницами>` — сборка JSON и вырезка фото в `public/images/menu/`. Без папки пересобирается только JSON. Когда меню зала появится в iiko, файл и скрипт больше не нужны.

Старые адреса `/menu/<блюдо>` перенаправляются на `/delivery/<блюдо>`.

### Дизайн

«Северный лес ночью»: токены в `src/app/(site)/globals.css`. Тёмная тема по умолчанию, светлая `.theme-paper` — для меню, корзины, оформления и страницы заказа. Шрифты Tenor Sans (заголовки) + Manrope. Макеты: `../design/preview.html`.

`node scripts/prepare-images.mjs ../design/img` готовит из исходников логотип (прозрачный WebP), гравюру и фото главной в `public/images/`. Фото главной — исходники для сида CMS; на сайте используются копии из админки. Плейсхолдер блюда без фото — `public/images/dish-placeholder.webp`.

### Кэширование

- Структура меню и цены: профиль `menu` (пересборка раз в 10 минут), тег `menu`.
- Меню со стоп-листом: профиль `stopList` (раз в 2 минуты), тег `stop-list`.
- Контент CMS: профиль `content`, тег `content` — сбрасывается сразу при сохранении в админке.
- При оформлении заказа цены, стоп-лист и условия доставки перепроверяются на сервере. Цены, пришедшие из браузера, не используются.
- Ручной сброс кэша: `POST /api/revalidate?secret=…&tag=menu|stop-list|content`. Нужен после изменений в базе в обход админки (скрипты `payload run`); в режиме разработки секрет не требуется.

## Деплой (VPS)

1. Node.js 20+, `npm ci`, `.env` с `PAYLOAD_SECRET`, `DATABASE_URL` (постоянный путь), Telegram, DaData.
2. Папку `media/` вынести в постоянное место (симлинк) — там загруженные фото.
3. `npm run build && npm run start` (через PM2 или systemd), Nginx с SSL перед ним.
4. На пустой базе первый старт применит миграции и заполнит контент. Затем — регистрация первого пользователя на `/admin`.
5. Бэкап: база + `media/` (например, ежедневно cron'ом).

## Подключение iiko — чек-лист

1. Получить у заказчика `apiLogin` (лицензия iikoCloud API).
2. Выяснить и записать в `.env`: `IIKO_ORGANIZATION_ID` (`/api/1/organizations`), `IIKO_TERMINAL_GROUP_ID` (`/api/1/terminal_groups`), `IIKO_EXTERNAL_MENU_ID` (`/api/2/menu`), ID типов оплат (`/api/1/payment_types`).
3. Сверить типы `lib/iiko/types.ts` и тело заказа в `lib/providers/order/iiko-cloud.ts` с актуальной документацией.
4. Добавить хост фото iiko в `images.remotePatterns` (`next.config.ts`), если он отличается от уже указанных.
5. Включить `MENU_PROVIDER=iiko`, проверить меню. Затем включить `ORDER_PROVIDER=iiko` и прогнать тестовые заказы на тестовой организации.
6. Настроить вебхук стоп-листа на `/api/revalidate`.
7. Проверить «популярные блюда» в админке: ID из myresto должны совпасть с iikoCloud — если меню другое (другое внешнее меню), выбрать заново.
