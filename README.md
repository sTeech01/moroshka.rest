## Перенос на другой компьютер

**Не всё лежит в git.** Скопируйте папку проекта целиком (`Морошка/`), а не только клонируйте репозиторий. Только на диске лежат:

| Что | Зачем | Если потерять |
|---|---|---|
| `site/.env.local` | Ключ сообщества ВКонтакте для уведомлений (`VK_GROUP_TOKEN`, `VK_CHAT_ID`), пароль демо-админки (`DEMO_PASSWORD`) | Заказы и брони с локального сайта не придут в беседу. Ключ — у сисадмина ресторана |
| `site/data/payload.db` | База CMS: тексты, настройки, афиша, пользователи админки | Сайт заполнится начальным контентом из `src/payload/seed`, все правки из админки пропадут |
| `site/media/` | Фото, загруженные в админке (VIP-зал, афиша, «О ресторане») | Эти фото пропадут со страниц |
| `design/`, файлы в корне `Морошка/` | Исходники дизайна, логотипа, видео (`design/video`), карточка предприятия, ТЗ | — |

Копировать **не нужно** (большие, пересоздаются сами): `site/node_modules/`, `site/.next/`.

**На новом компьютере:**

1. Установить Node.js **24** (проект проверялся на 24.18) и Git.
2. В папке `site`:
   ```bash
   npm ci
   npm run dev        # сайт: http://localhost:3000, админка: http://localhost:3000/admin
   ```
3. Для отправки в GitHub — войти в аккаунт `sTeech01` (`gh auth login` или Git Credential Manager при первом `git push`).

Если папка скопирована без `.git`: `git clone https://github.com/sTeech01/moroshka.rest.git site`, затем положить в `site` файлы из таблицы выше.

## Запуск и проверки

```bash
npm run dev          # разработка
npm run typecheck    # типы (сначала генерирует типы маршрутов Next)
npm run lint
npm run cms:check    # CMS без Next: что в базе, меню доставки и зала
npm run build        # боевая сборка (см. ниже)
```

- **Первый запуск на пустой базе** создаёт `data/payload.db` и заполняет её контентом из `src/payload/seed`.
- **Первый пользователь** регистрируется на `/admin` и автоматически становится администратором.
- **В dev `npm run dev` подхватывает `.env.local`.** Если там ключ ВК, тестовые заказы и брони **уходят в настоящую беседу сотрудников**. Без ключей заявки печатаются в консоль сервера.

**Боевая сборка локально** (Windows, cmd):

```bat
set PAYLOAD_SECRET=любая-длинная-строка
set DATABASE_URL=file:./data/build-check.db
npm run build
```

- `PAYLOAD_SECRET` в production обязателен.
- Собирать по рабочей `data/payload.db` нельзя: её схему синхронизирует dev-режим без миграций, и Payload в production остановит сборку вопросом «run migrations, data loss will occur?». Отвечать «y» нельзя. Для сборки нужна копия базы с отмеченными миграциями, её делает `npm run demo:build` (`demo/payload.db`; скопировать в `data/build-check.db`).
- `experimental.cpus: 4` в `next.config.ts` оставить: при 15 параллельных процессах Windows отказывала в создании процесса (`spawn EPERM` на «Collecting page data»).

## CMS (Payload)

Админка — `/admin`, на русском. Меню, цены и фото блюд в CMS **не** редактируются: они приходят из iiko (пока — из заглушки, см. ниже).

| Раздел админки | Что там | Где на сайте |
|---|---|---|
| Контент → Афиша | События: дата, обложка, описание. Прошедшие скрываются сами | `/events` |
| Контент → Промо и акции | Баннеры с датами показа: главная и/или меню и доставка | Главная, `/menu`, `/delivery` |
| Контент → Страницы | О ресторане, условия доставки, соглашение, оферта, правила | `/about`, низ `/delivery`, `/privacy-policy`, `/offer`, `/rules` |
| Контент → Медиа | Все загруженные фото. Оригинал ужимается до 2400 px и переводится в WebP | — |
| Страницы → Главная | Заголовок первого экрана (фон — видео `public/video/hero.mp4`), плитки «Кухня» и «Бар», **популярные блюда** (выбор из меню доставки) | `/` |
| Страницы → Банкеты и VIP-зал | Фото первого экрана, залы, галерея, текст | `/banquets` |
| Страницы → Бизнес-ланч | Вкл/выкл, расписание, позиции с ценами | `/business-lunch` |
| Настройки → Ресторан | Телефоны, адрес, часы, ВКонтакте/Telegram, координаты, реквизиты | Шапка, подвал, `/contacts` |
| Настройки → Доставка | Вкл/выкл, объявление, мин. сумма, стоимость, бесплатно от, часы приёма, слоты, самовывоз | Корзина, оформление, проверка заказа на сервере |
| Администрирование → Пользователи | Роли: администратор (всё) и редактор (контент) | — |

**Правка попадает на сайт сразу.** После сохранения хуки Payload сбрасывают кэш с тегом `content` (`src/payload/revalidate.ts`), деплой не нужен.

**Изменили поля коллекций или глобалов (`src/payload/**`)?**

```bash
npm run generate:types            # src/payload-types.ts
npm run generate:importmap        # если добавили/убрали свои компоненты админки
npm run migrate:create <название> # миграция для прода — закоммитить src/migrations
```

В dev схема базы синхронизируется сама. В продакшене при старте применяются миграции из `src/migrations` (`prodMigrations`). У «Главной» есть скрытые поля (`about*`, `banquet*`, `gallery`) от снятых с главной блоков. Они оставлены в схеме, чтобы не делать миграцию с удалением данных, и их можно удалить вместе с ближайшей миграцией.

**Payload CLI** на Node 24 работает только с `--use-swc` (режим tsx падает из-за undici). Все npm-скрипты уже с флагом; разовые скрипты — `npx payload run <файл.ts> --use-swc`.

## Уведомления о заказах, бронях и заявках

`src/lib/notify` — `notifyStaff()` отправляет сообщение во **все** настроенные каналы:

| Канал | Переменные | Сейчас |
|---|---|---|
| Беседа сотрудников ВКонтакте (от имени сообщества, `messages.send`) | `VK_GROUP_TOKEN`, `VK_CHAT_ID` (`2` или `2000000002`) | Работает, проверено 20.10.2026. Ключ — в `site/.env.local` |
| Telegram-чат | `TELEGRAM_BOT_TOKEN`, `TELEGRAM_CHAT_ID` | Не настроен |

- **Заявка считается отправленной**, если дошла хотя бы до одного канала. Сбои остальных пишутся в лог.
- **Без каналов:**
  - в dev — вывод в консоль;
  - на демо (Vercel) — демо-режим: заявка «принимается», клиенту видна пометка, что это демо;
  - на боевом сервере — ошибка «Не удалось отправить заказ», чтобы заказ не потерялся молча.
- **Сообщение о заказе** содержит номер, имя, телефон, адрес или «Самовывоз», время, оплату, состав и сумму. Шаблон — `src/lib/providers/order/telegram.ts` (`render`).

## Архитектура

```
src/
  app/(site)/          сайт: свой корневой layout, страницы, 404
  app/(payload)/       админка и REST API Payload (/admin, /api/<коллекция>) — файлы из шаблона Payload
  app/api/orders       приём заказа: валидация → пересчёт по меню и условиям доставки → OrderSink → (онлайн) PaymentGateway
  app/api/booking      бронь стола / заявка на банкет → notifyStaff
  app/api/address      подсказки улиц Губкинского (DaData)
  app/api/menu-options список блюд для виджета «Популярные блюда» в админке
  app/api/revalidate   сброс кэша меню (для вебхуков iiko)
  payload.config.ts    конфиг CMS (+ ветка демо для Vercel)
  payload/             коллекции, глобалы, доступы, хуки сброса кэша, сид, виджет админки
  lib/content.ts       чтение контента из Payload (локальный API) с кэшем
  lib/notify/          уведомления сотрудникам: Telegram, ВКонтакте
  lib/delivery.ts      условия доставки и расчёт стоимости — общий для браузера и сервера
  lib/iiko/            типы ответов iikoCloud и HTTP-клиент с токеном
  lib/menu/            доменная модель меню, маппер iiko → сайт, меню доставки и меню зала
  lib/providers/       адаптеры: MenuSource, OrderSink, PaymentGateway (mock ↔ real)
  lib/cart/pricing     цена позиции и проверка модификаторов — общая для браузера и сервера
  store/cart.ts        корзина (Zustand + localStorage)
data/iiko-mock/        заглушка iiko: меню доставки, меню зала, стоп-лист (формат iikoCloud)
demo/                  демо-данные для Vercel: база без личных данных и копия фото
public/video/          видео первого экрана главной и его кадр-заставка
scripts/               импорт меню, сборка меню зала, демо-данные, подготовка картинок, cms:check
```

### Провайдеры (переключаются в `.env`)

| Переменная | Сейчас | После подключения |
|---|---|---|
| `MENU_PROVIDER` | `mock` — читает `data/iiko-mock/*.json` | `iiko` — iikoCloud `/api/2/menu/by_id`, `/api/1/stop_lists` |
| `ORDER_PROVIDER` | `telegram` — заказ сообщением сотрудникам (ВКонтакте и/или Telegram) | `iiko` — `/api/1/deliveries/create` |
| `PAYMENT_PROVIDER` | `mock` — оплата «проходит» сразу | `yookassa` / `tbank` (реализовать в `lib/providers/payment/`) |
| `NEXT_PUBLIC_ONLINE_PAYMENT_ENABLED` | `false` — пункт «Онлайн» скрыт | `true` |

Заглушка меню хранится **в формате ответа iiko**, поэтому маппер `lib/menu/map-iiko.ts` работает одинаково для обоих источников. **В заглушке реальное меню доставки** из myresto (работает поверх iiko): ID блюд и организации — настоящие ID iiko. Обновить снимок: `npm run menu:import`.

### Два меню: «Меню» и «Доставка»

| Раздел | Что это | Источник |
|---|---|---|
| `/menu` | Меню зала: витрина без корзины, все блюда кухни | `getHallMenu()` → `data/iiko-mock/hall-menu.json`, позже — второе внешнее меню iiko (`IIKO_HALL_MENU_ID`, опц. `IIKO_HALL_PRICE_CATEGORY_ID`) |
| `/delivery` | Заказ: только то, что возят. Ниже — условия доставки из CMS | `getMenu()` → меню доставки iiko (`IIKO_EXTERNAL_MENU_ID`) |

- **Связь по ID блюда в iiko.** Если блюдо зала есть в доставке, у него ссылка «Можно заказать домой». Если у блюда доставки нет фото в iiko, берётся фото того же блюда из меню зала.
- **Меню зала перенесено со старого сайта** (moroshka.rest/menu-kitchen, 23 страницы-картинки). Данные — `scripts/hall-menu/source.mjs`, сборка JSON — `npm run menu:hall`. С аргументом `-- <папка со страницами>` скрипт заново вырезает фото в `public/images/menu/`.
- **Старые адреса** `/menu/<блюдо>`, `/menu-kitchen`, `/bar-menu`, `/privacy` перенаправляются на новые (`next.config.ts`).

### Главная

- **Первый экран — видео интерьера** (`public/video/hero.mp4`, 19 с по кругу, 3,7 МБ), вырезанное из ролика старого сайта; оригинал — `../design/video`. Пока видео грузится, а также при «уменьшить движение» или экономии трафика, показывается кадр `hero-poster.webp`.
- **Шапка** на страницах с `PageHero` (главная, банкеты) прозрачная, пока страница не прокручена. Это сделано CSS-селектором по атрибуту `data-hero-overlay`, а не по адресу страницы: `usePathname()` в layout ломал пререндер `/order/[id]`.
- **«Северная кухня дома»** — популярные блюда из админки. Если пусто, берётся по одному блюду с фото из разных разделов.

### Дизайн

- **Стиль «Северный лес ночью»:** токены в `src/app/(site)/globals.css`. Тёмная тема по умолчанию, светлая `.theme-paper` — для меню, доставки, корзины, оформления и страницы заказа.
- **Шрифты:** Tenor Sans (заголовки) + Manrope.
- **`node scripts/prepare-images.mjs ../design/img`** готовит логотип (`logo.png` на чёрном → прозрачный WebP), гравюру ягод и фото для начального наполнения CMS.
- **Фавикон** (`src/app/icon.png`, `apple-icon.png`, `favicon.ico`) — ягода из логотипа.

### Кэширование

- Структура меню и цены: профиль `menu` (раз в 10 минут), тег `menu`. Меню со стоп-листом: профиль `stopList` (раз в 2 минуты), тег `stop-list`.
- Контент CMS: профиль `content`, тег `content` — сбрасывается при сохранении в админке.
- При оформлении заказа цены, стоп-лист и условия доставки перепроверяются на сервере. Цены из браузера не используются.
- Ручной сброс: `POST /api/revalidate?secret=…&tag=menu|stop-list|content`. Нужен после правок базы в обход админки (`payload run`); в dev секрет не требуется.

## Демо на Vercel

https://moroshka-rest-h1nx.vercel.app — для показа заказчику. Пересобирается сам при каждом `git push` в `main`.

- **Вход в админку демо:** `demo@moroshka.rest`, пароль — `DEMO_PASSWORD` в `site/.env.local` (в репозиторий не кладём).
- **Переменные проекта Vercel:** только `PAYLOAD_SECRET`. Переменная `VERCEL` задаётся автоматически и включает режим демо.
- **Диск на Vercel только для чтения.**
  - База — копия `demo/payload.db`, при старте копируется в `/tmp`. Правки в админке живут до перезапуска сервера Vercel, у разных серверов свои копии.
  - Фото читаются из `demo/media`, загрузить новые нельзя.
  - Вход в админку без серверных сессий (`useSessions: false`), иначе выкидывало между серверами.
- **Заказы и брони никуда не уходят** (демо-режим `lib/notify`), клиенту показывается пометка. Чтобы демо слало в ВК, добавить `VK_GROUP_TOKEN` и `VK_CHAT_ID` в Vercel и сделать Redeploy.
- **Поисковики демо не индексируют** (robots и noindex).
- **Обновить контент демо** из локальной базы: `npm run demo:build` (пароль скрипт берёт из `.env.local`), затем коммит и push. Скрипт убирает настоящих пользователей и сессии, оставляет одного демо-пользователя.

## Деплой (боевой, VPS в РФ)

1. Node.js 24, `npm ci`, `.env` с `PAYLOAD_SECRET`, `DATABASE_URL` (постоянный путь вне папки релиза), `VK_GROUP_TOKEN` + `VK_CHAT_ID` и/или Telegram, DaData.
2. Папку `media/` вынести в постоянное место (симлинк) — там загруженные фото.
3. `npm run build && npm run start` (PM2 или systemd), Nginx с SSL перед ним.
4. На пустой базе первый старт применит миграции и заполнит контент. Затем — регистрация первого пользователя на `/admin`. Если переносится база с локального компьютера, отметить в ней миграции применёнными, как в `scripts/build-demo.mjs`.
5. Бэкап: база + `media/` (например, ежедневно cron'ом).

## Подключение iiko — чек-лист

1. Получить у заказчика `apiLogin` (лицензия iikoCloud API).
2. Выяснить и записать в `.env`:
   - `IIKO_ORGANIZATION_ID` (`/api/1/organizations`);
   - `IIKO_TERMINAL_GROUP_ID` (`/api/1/terminal_groups`);
   - `IIKO_EXTERNAL_MENU_ID` и, если заведут меню зала, `IIKO_HALL_MENU_ID` (`/api/2/menu`);
   - ID типов оплат (`/api/1/payment_types`).
3. Сверить типы `lib/iiko/types.ts` и тело заказа в `lib/providers/order/iiko-cloud.ts` с актуальной документацией.
4. Добавить хост фото iiko в `images.remotePatterns` (`next.config.ts`), если он отличается от указанных.
5. Включить `MENU_PROVIDER=iiko`, проверить меню. Затем `ORDER_PROVIDER=iiko` и тестовые заказы на тестовой организации.
6. Настроить вебхук стоп-листа на `/api/revalidate`.
7. Проверить «популярные блюда» в админке: ID из myresto должны совпасть с iikoCloud.
